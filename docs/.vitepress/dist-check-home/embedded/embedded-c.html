03 · 嵌入式 C 与寄存器思维 ​

核心 约 40 min寄存器就是有地址的内存，位操作是基本功，volatile 和原子性是分水岭

本章的第一个概念——寄存器为什么就是内存——单独抽成了卡片：。

结论先行 ​

  1. 寄存器 = 占据固定地址的一小块内存。所谓「配置外设」，本质就是往这些地址里写特定的数；C 语言里用指针（通常是厂家定义好的结构体指针）访问它们。
  2. 位操作只有四个动作：置位 |= (1<<n)、清零 &= ~(1<<n)、翻转 ^= (1<<n)、读位 (reg>>n)&1。清零必须取反，直接 &= (1<<n) 是经典错误。
  3. volatile 告诉编译器「这个变量会被你不知道的方式改变，别优化掉对它的读写」。硬件寄存器、中断里改的全局变量、RTOS 共享变量，三者都必须加。
  4. 改寄存器的某一位要用「读—改—写」，但这不是原子的；STM32 提供 BSRR 寄存器实现单条指令的原子位操作。
  5. 嵌入式 C 的额外纪律：慎用 malloc、注意结构体对齐、全局/静态变量要算进 RAM、const 常量放 Flash。

一、内存映射：寄存器是有地址的内存 ​

完整的地址空间划分与偏移表见 ；下面先看它长什么样。

Cortex-M 有 4 GB 的线性地址空间（32 位地址），芯片厂商把它切成几块：

地址区间放什么
0x0000 0000 ~代码区（Flash 的别名，实际从 0x0800 0000 开始）
0x0800 0000 ~Flash：程序代码和 const 常量
0x2000 0000 ~SRAM：全局变量、栈、堆
0x4000 0000 ~外设寄存器（APB1 / APB2 / AHB 各总线挂的外设）
0xE000 0000 ~Cortex-M 内核的系统控制块（NVIC、SysTick 等）

以 F103 为例，GPIOA 的寄存器组从 0x4001 0800 开始，内部按固定偏移排列：

偏移寄存器作用
0x00CRL配置 Pin0~7（每脚 4 位）
0x04CRH配置 Pin8~15（每脚 4 位）
0x08IDR输入数据（读引脚电平）
0x0CODR输出数据（写引脚电平）
0x10BSRR原子置位/清零
0x14BRR清零（等价于 BSRR 高 16 位）

CMSIS 库把这些地址定义成一个结构体指针，于是你可以写：

c
#define GPIOA_BASE 0x40010800UL
typedef struct {
  volatile uint32_t CRL, CRH, IDR, ODR, BSRR, BRR, LCKR;
} GPIO_TypeDef;
#define GPIOA ((GPIO_TypeDef *)GPIOA_BASE)

GPIOA->ODR |= (1 << 5);   // 就是往 0x4001080C 这个地址写

这一点想通了，后面所有外设就都通了：UART 的 DR 寄存器、定时器的 CNT、ADC 的 DR，全都是「有名字的地址」，操作它们就是读写内存。

二、位操作的四个动作 ​

外设寄存器几乎从不「整个赋值」——因为一个 32 位寄存器里往往塞了十几个互不相关的配置字段，你只想改其中一位，绝不能动其他位。于是有了四个标准动作：

动作写法含义
置位（把某位写成 1）reg |= (1 << n)OR 上「只有第 n 位为 1」的掩码，其余位不变
清零（把某位写成 0）reg &= ~(1 << n)AND 上「只有第 n 位为 0」的掩码
翻转（1↔0）reg ^= (1 << n)异或，同掩码翻转两次回到原值
读位(reg >> n) & 1右移到最低位再屏蔽其余位

例 1 · 置位：把寄存器第 3 位写成 1

寄存器初值 0x0000 00A0（二进制 1010 0000，即 bit5 和 bit7 为 1）。要把 bit3 置 1：

0x00A0  ∣  (1≪3)=0x00A0  ∣  0x0008=0x00A8\text{0x00A0} \;|\; (1 \ll 3) = \text{0x00A0} \;|\; \text{0x0008} = \text{0x00A8} 0x00A0∣(1≪3)=0x00A0∣0x0008=0x00A8

二进制：1010 0000 → 1010 1000，bit5、bit7 原封不动。这就是 OR 的性质：任何位 OR 0 保持不变，OR 1 变成 1。

例 2 · 清零：把第 5 位写成 0（最易错的一步）

承接上一步的 0x00A8，要把 bit5 清 0。

正确做法——掩码取反：

0x00A8  &  ∼(1≪5)=0x00A8  &  0xFFFF FFDF=0x0088\text{0x00A8} \; \& \; \sim(1 \ll 5) = \text{0x00A8} \; \& \; \text{0xFFFF FFDF} = \text{0x0088} 0x00A8&∼(1≪5)=0x00A8&0xFFFF FFDF=0x0088

错误做法（初学者高频）——忘了取反：

0x00A8  &  (1≪5)=0x00A8  &  0x20=0x0020\text{0x00A8} \; \& \; (1 \ll 5) = \text{0x00A8} \; \& \; \text{0x20} = \text{0x0020} 0x00A8&(1≪5)=0x00A8&0x20=0x0020

结果是除了 bit5 之外所有位都被清掉了，整个寄存器被毁。记住口诀：置位用原掩码，清零用反掩码。

例 3 · 翻转与读位

承接 0x0088，翻转 bit7：

0x0088  ⊕  (1≪7)=0x0088  ⊕  0x80=0x0008\text{0x0088} \; \oplus \; (1 \ll 7) = \text{0x0088} \; \oplus \; \text{0x80} = \text{0x0008} 0x0088⊕(1≪7)=0x0088⊕0x80=0x0008

bit7 从 1 变成 0。翻转的性质是可逆：再执行一次 ^= (1<<7) 又会变回 0x0088，所以 LED_Toggle 这类操作用异或最自然。

读位：读当前值 0x0008 的 bit5：

(0x0008≫5)  &  1=0  &  1=0(0\text{x}0008 \gg 5) \; \& \; 1 = 0 \; \& \; 1 = 0 (0x0008≫5)&1=0&1=0

即 bit5 当前是 0。注意读位时先移位再屏蔽的顺序不能颠倒——若写成 reg & (1<<5)，得到的会是 0x00 或 0x20，而不是干净的 0/1。

例 4 · 写多位的配置字段（位域写入）

配置 GPIO 时，每个引脚占 4 位（2 位模式 + 2 位速度）。要把 0x00A0 的 bit[3:2] 这个两位的字段改写成 01，不能只清零再置位，得先把整个字段抹掉，再写入新值：

c
uint32_t mask = 0b11 << 2;              // 字段掩码：bit[3:2]
reg = (reg & ~mask) | (0b01 << 2);      // 先清空字段，再写入值

代入验证：

0x00A0  &  ∼0x0C=0x00A0  &  0xFFFF FFF3=0x00A0\text{0x00A0} \; \& \; \sim 0\text{x0C} = \text{0x00A0} \; \& \; \text{0xFFFF FFF3} = \text{0x00A0} 0x00A0&∼0x0C=0x00A0&0xFFFF FFF3=0x00A00x00A0  ∣  (1≪2)=0x00A4\text{0x00A0} \; | \; (1 \ll 2) = \text{0x00A4} 0x00A0∣(1≪2)=0x00A4

结果 0x00A4，其中 bit[3:2] = 01（因为 0xA4 = 1010 0100，bit3=0、bit2=1）。

为什么不能分两步（先 |= (1<<2) 再 &= ~(1<<3)）？在单线程里结果相同，但如果中间被中断打断，硬件会短暂看到一个中间态（字段先变成 11 之类），对配置敏感的寄存器（如时钟分频）可能引发故障。所以配字段要一次算好一次写入。

三、volatile：别让编译器把你的代码优化没了 ​

编译器会做一件很聪明的事：如果一个变量在某段代码里没被写过，它就认为这个值不会变，把重复读取优化掉。在 PC 上这没问题，但在嵌入式里，有些变量会被编译器看不见的东西改变——硬件、中断、另一个任务。

三种必须加 volatile 的场景：

c
// ① 硬件寄存器（CMSIS 的结构体成员全部带 volatile）
while ((USART1->SR & (1 << 5)) == 0) { }   // 等待发送完成标志

// ② 中断服务程序里修改的标志
volatile uint8_t flag = 0;
void HAL_GPIO_EXTI_Callback(uint16_t pin) { flag = 1; }
int main(void) { while (!flag) { } /* ... */ }

// ③ RTOS / 多线程共享的变量
volatile uint32_t tick_count;

不加 volatile 会发生什么：while(!flag); 里，编译器发现循环体不修改 flag，就把它优化成「读一次到寄存器，然后死循环」——中断明明把 flag 置 1 了，主循环却永远看不到。这类 bug 极其隐蔽：开优化（-O2）才出现，关优化（-O0）一切正常。

volatile 不保证什么：它只保证「每次都真的去内存读/写」，不保证原子性，也不能替代互斥锁。多字节变量的跨任务保护要靠关中断或 RTOS 的同步机制。

四、原子性：BSRR 为什么存在 ​

看这行很常见的代码：

c
GPIOA->ODR |= (1 << 5);   // 看起来是「只改 bit5」

它编译后其实是三步机器操作：读 ODR → 或运算 → 写回 ODR。如果在这三步之间来了个中断，中断里也改了 ODR 的其他位，那么中断返回后，主程序写回的旧值会把中断的修改覆盖掉。

STM32 为此提供了 BSRR（Bit Set/Reset Register）：

c
GPIOA->BSRR = (1 << 5);          // 低 16 位：置位 → bit5 = 1
GPIOA->BSRR = (1 << (5 + 16));   // 高 16 位：清零 → bit5 = 0

写入 BSRR 是一次写操作，硬件内部完成置位/清零，不存在「读—改—写」的窗口，因此是原子的——中断里改 GPIO 可以放心用。

这也是 HAL 库 HAL_GPIO_WritePin 内部用 BSRR/BRR 而不是 ODR |= 的原因之一。

五、嵌入式 C 的额外纪律 ​

主题纪律原因
动态内存尽量不用 malloc / free内存碎片；失败时难以恢复；确定性差
栈大数组不要放函数内；递归要谨慎栈溢出会静默破坏内存，且默认栈可能只有几 KB
结构体对齐与硬件/协议对应的结构体要检查对齐编译器会插填充字节，导致结构体大小和成员偏移与预期不符
const常量表加 const会被放进 Flash 而不是占用宝贵的 RAM
static限制作用域，避免全局污染也便于编译器优化
浮点M0/M3 无 FPU，float 运算是软件模拟，很慢需要浮点运算选 M4 或改用定点

结构体对齐的例子：

c
typedef struct {
  uint8_t  a;   // 偏移 0
  uint32_t b;   // 偏移 4（编译器插了 3 字节填充）
  uint8_t  c;   // 偏移 8
} Bad;          // sizeof = 12，不是 6

按成员从大到小排列，或用 __attribute__((packed))（但会带来非对齐访问的性能损失甚至硬件错误）来消除填充。

六、工程实例 ​

为什么 HAL 库的 handle 里到处是 volatile：打开 stm32f1xx_hal_uart.h，你会看到 UART_HandleTypeDef 里的状态成员带 __IO（就是 volatile 的宏）。因为 UART 的收发状态会被中断服务程序修改，主程序轮询它时必须每次真正读内存。

一个真实的隐蔽 bug：某项目用 while(!tx_done); 等待 DMA 发送完成，tx_done 在 DMA 中断里置位。Debug 版本（-O0）正常，Release（-O2）死机。原因就是 tx_done 没加 volatile，被优化成了只读一次。加上 volatile 后两个版本都正常——这类问题只在优化后才暴露，所以要尽早用 Release 配置编译验证。

七、易错清单 + 自检 ​

  • [ ] 清零忘了取反：&= ~(1<<n) 才是清零，&= (1<<n) 会毁掉整个寄存器
  • [ ] 读位顺序：(reg >> n) & 1，先移位后屏蔽
  • [ ] 改多位字段：先 & ~mask 清空，再 | value 一次写入
  • [ ] 中断/RTOS 共享的变量没加 volatile：不优化时正常，开 -O2 后死等
  • [ ] volatile 不等于原子：多字节共享变量仍需关中断或用 RTOS 同步
  • [ ] 中断里改 GPIO 用 ODR |=：有读—改—写竞态，改用 BSRR
  • [ ] 函数里开大数组导致栈溢出：改成 static 或全局
  • [ ] 结构体直接映射到硬件/协议：务必检查对齐和填充

自检：写出「把 32 位寄存器 reg 的 bit7 清零、bit3 置位、其余位不变」的两种写法（普通写法 + BSRR 原子写法）；并说出 volatile 必须用的三个场景。（答案：reg = (reg & ~(1<<7)) | (1<<3);；GPIOx->BSRR = (1<<(7+16)) | (1<<3);；硬件寄存器、中断修改的变量、多任务共享变量）
