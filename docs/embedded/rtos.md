# 11 · RTOS 入门（FreeRTOS）

<Meta time="45 min" level="核心" note="什么时候该上 RTOS、任务怎么切、共享资源怎么保护" />

## 结论先行

1. **裸机 super-loop 的根本问题是「阻塞」**：任何一个耗时的操作（等待传感器、发送数据、软件延时）都会拖住其他所有响应。
2. **RTOS 用「多任务 + 抢占调度」解决**：每个任务有自己的栈和优先级，**高优先级任务一旦就绪就立刻抢占 CPU**，不用等别人跑完。
3. **任务间通信用三件套**：**队列**（传数据）、**信号量**（同步/通知）、**互斥量**（保护共享资源，且带优先级继承）。
4. **不是所有项目都需要 RTOS**：只有「多组独立时序 + 复杂交互」时才值得引入；简单项目裸机（中断 + 状态机）反而更可靠。
5. **三大坑**：栈溢出、优先级反转、以及**在中断里调用了不带 `FromISR` 后缀的 API**。

## 一、裸机 super-loop 的极限

典型的裸机结构是「中断置标志 + 主循环轮询处理」：

```c
while (1) {
  if (flag_key)   { handle_key();   flag_key = 0; }
  if (flag_uart)  { handle_uart();  flag_uart = 0; }
  if (flag_adc)   { handle_adc();   flag_adc = 0; }
  // ...
}
```

这套结构清晰、开销小，但有一个致命弱点：**任何一个处理函数耗时长，其他所有事件的响应就被推迟**。

::: tip 例 1 · 裸机下的响应延迟
某系统主循环里有三个处理：

| 处理 | 耗时 |
| --- | --- |
| 传感器采集与计算 | 80 ms |
| 屏幕刷新（SPI 刷一屏） | 50 ms |
| 按键处理 | 1 ms |

一轮循环 131 ms。若按键恰好在「传感器采集」刚开始时按下，它要等 **80 ms** 才被处理——**人手能明显感觉到迟钝**（人类感知阈值约 100 ms）。

更糟的是：如果传感器处理里有一个 `HAL_Delay(100)` 之类的等待，整个系统的响应就变成 180 ms 以上，且**响应时间是变化的**（取决于按键发生在循环的哪个阶段）——这在实时系统里是致命的，因为你无法保证最坏响应时间。

**RTOS 的做法**：把三件事拆成三个任务，按键任务设为最高优先级。按键一就绪就**立刻抢占**正在跑的采集任务，1 ms 处理完再回去——响应时间稳定在 1 ms 量级，且**与系统当时在做什么无关**。
:::

## 二、RTOS 的核心概念

| 概念 | 含义 |
| --- | --- |
| **任务（Task）** | 一个独立的执行流，有自己的栈、优先级和状态。本质是一个永不返回的函数 |
| **调度器（Scheduler）** | 决定「此刻哪个任务获得 CPU」。FreeRTOS 默认**抢占式 + 优先级 + 同优先级时间片轮转** |
| **任务状态** | 运行（Running）、就绪（Ready）、阻塞（Blocked）、挂起（Suspended） |
| **时间片（Tick）** | 系统心跳，由 SysTick 产生，周期由 `configTICK_RATE_HZ` 决定（常设 1000 → 1 ms） |
| **上下文切换** | 保存当前任务的寄存器到它的栈、恢复下一个任务的寄存器 |

```c
void vTaskBlink(void *arg) {
  for (;;) {                          // 任务函数必须是无限循环，不能返回
    HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin);
    vTaskDelay(pdMS_TO_TICKS(500));   // 阻塞 500 ms，让出 CPU
  }
}

xTaskCreate(vTaskBlink, "blink", 128, NULL, 2, NULL);  // 栈深 128、优先级 2
vTaskStartScheduler();                 // 启动调度器，此后不再返回
```

**关键区别**：`vTaskDelay` 与 `HAL_Delay` 完全不同——前者**让出 CPU**（其他任务可以跑），后者是**空转死等**（占着 CPU 什么都不干）。

::: tip 例 2 · 抢占调度的时间线
三个任务：低（优先级 1）、中（优先级 2）、高（优先级 3）。低、中在 t=0 就绪，高在 **t=2** 就绪。

| 时刻 | 运行的任务 | 说明 |
| --- | --- | --- |
| 0~2 | 中 | 中优先级高于低，先跑 |
| **2~5** | **高** | 高优先级在 t=2 就绪，**立刻抢占**中 |
| 5~7 | 中 | 高优先级跑完，中接着跑 |
| 7~10 | 低 | 中跑完，才轮到低 |
| 10+ | 空闲 | 全部完成，运行空闲任务 |

**要点**：抢占发生在**高优先级任务变为就绪的那一刻**（可能是中断里释放了一个信号量），而不是等到当前任务的时间片用完。这是「实时」的含义——**可预期的响应时间**。
:::

## 三、任务间通信：队列、信号量、互斥量

| 机制 | 用途 | 特点 |
| --- | --- | --- |
| **队列 Queue** | 任务间**传数据**（FIFO） | 可传结构体；可阻塞等待；是首选的数据通道 |
| **二值信号量** | **同步/通知**（「事情发生了」） | 不传数据；**没有**优先级继承 |
| **计数信号量** | 资源计数（如「还有几个缓冲可用」） | — |
| **互斥量 Mutex** | **保护共享资源**（互斥访问） | **带优先级继承**；必须同一任务「获取—释放」配对 |
| **事件组** | 等待多个事件的组合（与/或） | 适合「等 A 和 B 都发生」 |

```c
// 队列：中断里收串口数据，任务里解析
QueueHandle_t q = xQueueCreate(32, sizeof(uint8_t));
// 发送（中断里必须用 FromISR 版本）
xQueueSendFromISR(q, &byte, &pxHigherPriorityTaskWoken);
// 接收（任务里阻塞等待）
uint8_t b;
if (xQueueReceive(q, &b, portMAX_DELAY) == pdTRUE) { /* 处理 b */ }
```

## 四、优先级反转

::: tip 例 3 · 优先级反转是怎么发生的，怎么修
**场景**：任务 L（低）持有一个互斥量访问共享资源；任务 H（高）就绪后抢占，但需要同一个互斥量 → **阻塞**；此时任务 M（中）就绪 → 它的优先级高于正在持锁的 L → **M 抢占 L 开始运行**。

**结果**：最高优先级的 H 在等锁，而中优先级的 M 却在跑——**H 被比它优先级低的任务挡住了**，而且被挡多久取决于 M 跑多久，完全不可预期。1997 年火星探路者号（Mars Pathfinder）在轨重启的著名故障，根源就是优先级反转。

**解法：优先级继承**。当高优先级任务等待某个互斥量时，**临时把持锁的低优先级任务提升到等待者的优先级**，使得中优先级任务无法插队，L 能尽快跑完释放锁。

**关键实践**：

- 保护共享资源要用 **mutex**（`xSemaphoreCreateMutex`，带优先级继承），**不要用二值信号量**——后者没有优先级继承，无法避免这个问题；
- 临界区（持锁时间）**越短越好**：只在真正访问共享资源的那几行加锁，不要在锁里做打印、延时等耗时操作；
- 若能用**队列**代替共享变量，就优先用队列——从根源上消除共享。
:::

## 五、任务栈：最容易悄悄炸掉的地方

每个任务有独立的栈，大小在 `xTaskCreate` 时指定。**单位是 `StackType_t`（32 位下 4 字节）**，所以：

$$\text{栈字节数} = usStackDepth \times 4$$

例如 `usStackDepth = 128` → 512 字节。

::: tip 例 4 · 估算任务栈并留余量
某任务会：调用若干层函数（最深约 3 层）、每层若干局部变量（合计约 80 字节），并调用 `printf`（`printf` 内部的格式化缓冲可能吃掉 **500~1000 字节**）。

$$\text{估算} = \underbrace{80}_{\text{局部变量}} + \underbrace{3 \times 32}_{\text{调用帧}} + \underbrace{1000}_{\text{printf}} + \underbrace{100}_{\text{浮点/上下文}} \approx 1300\ \text{字节}$$

换算成栈深度：$1300 / 4 = 325$，取 **384**（约 1.5 KB）并留余量。

**验证方法**（强烈建议）：FreeRTOS 提供 `uxTaskGetStackHighWaterMark()` 查询「历史最小剩余栈」，即栈的高水位线：

```c
printf("剩余栈: %lu words\n", uxTaskGetStackHighWaterMark(NULL));
```

运行时打印这个值，**如果剩余量很小（接近 0），说明栈快溢出了**。开发阶段应给每个任务查一次。

**栈溢出的可怕之处**：它不会立刻报错，而是**静默破坏相邻内存**——表现为「某个变量莫名其妙变了」「程序跑几天后死机」，极难定位。所以要么开 `configCHECK_FOR_STACK_OVERFLOW`，要么主动查高水位线。
:::

## 六、中断与 RTOS 的配合

**铁律**：**在中断服务程序里，只能调用带 `FromISR` 后缀的 API**（`xQueueSendFromISR`、`xSemaphoreGiveFromISR`……）。普通版本可能触发任务切换，而中断上下文里切换任务会导致系统崩溃。

```c
void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart) {
  BaseType_t xHigherPriorityTaskWoken = pdFALSE;
  xQueueSendFromISR(uart_queue, &rx_byte, &xHigherPriorityTaskWoken);
  portYIELD_FROM_ISR(xHigherPriorityTaskWoken);   // 若有更高优先级任务被唤醒，立刻切换
}
```

**另一个要点**：**中断优先级与 RTOS 的关系**。FreeRTOS 能管理的中断优先级是有上限的（由 `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY` 决定）。**优先级高于这个值的中断不受 RTOS 管理**，里面绝不能调用任何 FreeRTOS API（连 `FromISR` 版本都不行）——这是很多人踩的坑。

## 七、什么时候不需要 RTOS

| 场景 | 建议 |
| --- | --- |
| 逻辑简单、只有一两条时序 | **裸机**（中断 + 状态机），可靠且省资源 |
| RAM < 8 KB 的小芯片 | 裸机（每个任务栈都要占 RAM） |
| 多组独立时序（采集 + 通信 + UI） | **上 RTOS** |
| 需要复杂协议栈（网络、USB、文件系统） | **上 RTOS**（这些协议栈本身就依赖任务） |
| 硬实时、微秒级响应 | 用**中断**保证，而不是靠提高任务优先级 |

RTOS 的代价：额外的 RAM（任务栈）、额外的 CPU 开销（上下文切换）、以及更高的调试难度（竞态、死锁）。**不要为了「显得专业」而上 RTOS**。

## 八、易错清单 + 自检

- [ ] **在中断里用了不带 `FromISR` 的 API** → 系统崩溃
- [ ] **中断优先级高于 RTOS 管理上限**，却在里面调了 FreeRTOS API
- [ ] **用二值信号量当互斥量用** → 没有优先级继承，会反转
- [ ] **任务栈太小** → 静默破坏内存（用高水位线检查）
- [ ] **任务函数里写了 `return` 或不是无限循环** → 任务结束会跑飞
- [ ] **用 `HAL_Delay` 而不是 `vTaskDelay`** → 占着 CPU 空转，其他任务无法运行
- [ ] **在持锁期间做耗时操作**（打印、延时）→ 加剧优先级反转
- [ ] **共享变量/资源没加保护**（关中断、互斥量或队列）

**自检**：抢占式调度中，高优先级任务在什么时刻获得 CPU？优先级反转的解法是什么？`usStackDepth = 128` 对应多少字节栈？（答案：它变为就绪的那一刻立即抢占；优先级继承（用 mutex 而非二值信号量）；512 字节）
