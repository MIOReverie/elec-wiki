# 14 · RTC、看门狗与 Flash 编程

<Meta time="45 min" level="了解" note="三件事共用一条主线：时间要准、跑飞要能复位、固件要能改" />

数据记录仪记了半年，厂里拉了一次闸，第二天早上你打开记录，时间戳全回到了 2020 年 1 月 1 日。芯片一上电，计数器是从 0 数起的，没有电池就没人告诉它现在几点。电机控制器在客户现场偶尔死机，指示灯还亮着，说明程序卡在某个死循环里，可你把调试器接上去，什么也读不到。至于想给已经装到现场的设备修一个 bug，才发现那块 Flash 焊死了，下载器插不进去。

三台设备三种毛病，解法是同一类：让芯片自己多长几个器官。一个掉电也记得时间（RTC），一个发现程序不动了就自己重启（看门狗），还有一个能装下并改写自己的代码（片上 Flash）。

用到的符号：$f_{osc}$（晶振频率，RTC 用 32768 Hz 外部晶振）、$N_{pre}$（预分频系数，prescaler，把高频时钟除小到目标频率的整数因子）、$f_{tick}$（计数频率，分频后每秒送给计数器的脉冲数）、$T_{out}$（超时时间，watchdog 溢出前允许的最长间隔）、$T_{win}$（窗口期，window，看门狗允许喂狗的时间窗口宽度）、$ARR$（自动重装载值）、$N_{erase}$（擦写次数，flash endurance，单位次）。

正文要用到的几个说法，先各给一句：

- VBAT：芯片上一枚专门给 RTC 和备份域供电的电池引脚，接纽扣电池后主电断掉，RTC 继续走时。
- 备份域（backup domain）：由 VBAT 供电的一小块电路，装着 RTC 的计数器、闹钟和一小片 SRAM，与主电源无关。
- 窗口期：一个允许操作的时刻范围，WWDG 在这个范围之外喂狗也算错。
- 页擦除（page erase）：Flash 只能整页清零，不能单独改写页里的某几个字节。
- IAP（In-Application Programming，在应用编程）：应用程序自己调用内部 Flash 的编程接口改写自己所在的 Flash；Bootloader 是复位后先跑的那段小程序，负责判断该跳到哪个 App。
- RDP（Read-Debug Protection，读保护）：把芯片的调试口锁上，让普通办法读不出 Flash 里的内容。
- LSI（Low-Speed Internal，内部低速时钟）：芯片内部自带的约 40 kHz 振荡器，不依赖外部晶振，主要喂独立看门狗。

数学上只有乘除与取整，没有复数、没有微积分。
:::

## 一、RTC：掉电之后时间还对

RTC（Real-Time Clock，实时时钟）在芯片里是个很孤僻的模块。它不挂在系统主时钟上，只认一颗 32768 Hz 的外部晶振（LSE，低速外部时钟），所以你把主时钟配错、HSE 干脆没起振、PLL 锁不住，它都不受影响，照样一秒一秒往下走。

既然它这么独立，那颗电池接在哪里、又是谁在给谁供电，就值得先弄明白。

为什么偏偏选 32.768 kHz？因为 $32768 = 2^{15}$，用两次二分频就能从它得到 1 Hz，而二分频是数字电路里最简单、也最准的一件事。频率要是选成 2 的整数次幂之外的值，就得搬出麻烦得多的除法器。顺带一句，32.768 kHz 落在人耳听觉下限之下（人耳约 20 Hz ~ 20 kHz），所以它安静，对辐射和功耗也都友好。

至于预分频，你可以把它想成计数器前面的一道闸门，每 N 个脉冲才放行一个。晶振每秒敲 32768 下，预分频 128 之后闸门只放行 256 下/秒（32768 ÷ 128 = 256），再经 256 分频，就只剩 1 下/秒。代价也很直接：分频系数越大，计时越慢、分辨率越低，这是所有分频链共有的毛病。

STM32 的 RTC 里分三段：最前面一级 PRL 预分频是你能配的，后面 128 与 256 两段焊死在硬件里。所以能调的只有 PRL，它先把 32768 Hz 除到一个中间值，后面那两级再一路除到 1 Hz。秒脉冲想快一点或慢一点，动的都是 PRL。

### 1.2 从秒到年月日：计数器怎么进位

拿到 1 Hz 之后，剩下的就是纯数字逻辑，和你手算电子表一模一样。

- 预分频计数器（PRL）接 1 Hz，每秒减 1，减到 0 溢出，产生一个秒更新事件；
- 秒/分/时计数器每收到一次秒更新就加一，秒从 59 变 60 就清零，同时给分钟进一；
- 日期计数器知道每个月的天数（28/29/30/31），也知道闰年规则（第 4 年一闰，百年号要能被 400 整除才闰）。

闰年这条规则得单独说。教科书里的「四年一闰」到 2100 年会出错。公历的完整规则是：能被 4 整除但不能被 100 整除的年要闰，能被 400 整除的年照闰。1996 年闰、2000 年闰、1900 年不闰、2100 年不闰。写进代码时别偷懒。

### 1.3 闹钟、唤醒与备份域

报时之外，RTC 还有两件实用的本事。闹钟（alarm）可以在某个时刻产生一个中断，低功耗设备靠它定时唤醒 MCU，比一直开着定时器轮询省电得多；唤醒定时器（wake-up timer）则是一个可编程的倒计时，到点产生一次唤醒事件。

真正让 32.768 kHz 这个节拍在断电后活下来的，是备份域（backup domain）和 VBAT。

这里有一条工程纪律：时间设对之后，必须把后备寄存器的访问打开（STM32 上是 `RCC_BDCR` 里的备份域访问使能），否则每次复位 RTC 都会被重新初始化，时间白设。这个开关还有连带效应，它被打开过之后，普通调试器就不能再改写 Flash 了，因为调试口的擦除动作会破坏备份域。所以要改程序，得先把备份域写保护打开再复位。

步骤：

1. 分频因子：$32768 / 128 = 256\ \text{Hz}$，再 $256 / 256 = 1\ \text{Hz}$ ✓。*（为什么先除 128：STM32F1 的 RTC 内部固定是「PRL 预分频（可配 20 位）+ 128 + 256」两级，128 和 256 是硬件焊死的，只有最前面那级 PRL 可配。所以可配因子必须让最终结果是 32768 的整数倍。）*
2. 唤醒周期：10 分钟 = 600 秒。唤醒定时器直接数秒，所以计数器装载 599。*（为什么是 599 不是 600：定时器是「装载值 → 减到 0 触发」的向下计数，装 599 时它数 599、598 … 1、0，一共经过 600 个 1 Hz 脉冲间隔，也就是 600 秒整。如果装 600，就变成 601 秒。）*
3. 一年多少秒：2024 年是闰年（能被 4 整除、不能被 100 整除，且 2024 ÷ 4 = 506 没有余数），全年 366 天。

$$366 \times 24 \times 3600 = 31\,622\,400\ \text{s}$$

回代验算：用 RTC 自己的算法反推，2024-01-01 到 2025-01-01 跨过的月份天数是 31 + 29（2 月，闰年）+ 31 + 30 + 31 + 30 + 31 + 31 + 30 + 31 + 30 + 31 = 366 天，再乘 86400 s/天得 31 622 400 ✓。软件交叉验算：`366 * 24 * 3600 === 31622400` 为真 ✓。分频再算一遍：$128 \times 256 = 32768$，$32768 / 32768 = 1$ ✓。
:::

三件事到这里都钉住了：分频因子要整除 32768，唤醒定时器数的是秒、装载值要减一，闰年看的是四百年一闰。换一个器官：程序死了，谁来发现。

## 二、看门狗：程序跑飞了怎么自己回来

| --- | --- | --- |

| 判据 | 只有「超时」 | 「超时」+「太早」 |
| 喂狗时机 | 任意时刻都可以 | 必须在窗口期内，早了晚了都复位 |

IWDG 用 LSI，这就是它「独立」的全部含义。LSI 是芯片内部自带的振荡器（Low-Speed Internal），不需要外部晶振，供电和时钟树跟 HSE、PLL 那条路没有任何牵扯。你把时钟树配错、卡在启动阶段，IWDG 照样在正常计时，最后照样把芯片复位。WWDG 用 PCLK，主时钟一挂它跟着停，兜底能力当场消失。

WWDG 的「窗口」把整个超时周期切成两段：一段叫窗口期（window，允许喂狗的那一小段时间），另一段就是不许动手的开口期。WWDG 一启动，窗口是关的，你喂得太早会被判为错误；等计数器减到某个阈值以下，窗口才打开，这时喂狗才算数。

所以结果是：喂得太早会复位，说明程序节奏不正常、循环跑得太快；喂得太晚也复位，说明程序卡住了。这才让 WWDG 抓到 IWDG 抓不到的一类故障：程序没死，但跑得不对。

喂狗这件事，最常被搞错的是位置。

- ✅ 主循环末尾喂狗：主循环能转到这一行，说明整条流程还在正常流转；
- ❌ 在定时器中断里喂狗：定时器中断是硬件机制，主循环卡死时它照样按时触发。于是「主循环已死」这个本该报警的故障被中断悄悄掩盖，看门狗永远不会响，等于白开；

:::

### 2.3 例题：算 IWDG 超时时间与 WWDG 窗口

::: tip 例 2 · 配一个 4 秒超时的 IWDG，并检查 WWDG 的喂狗窗口
**题目**：

1. LSI ≈ 40 kHz。要 IWDG 在 4 秒后复位，选预分频系数与重装载值各是多少？
2. 这个 4 秒超时是否落在 IWDG 的能力范围内？
3. 若 WWDG 的时钟是 PCLK = 36 MHz，预分频 8，请给出：一个计数值对应多少时间、总超时时间多长、窗口期多宽？

先把「计数频率」和「计数个数」分开，别直接套公式：分子是数了多少个数，分母是每秒数多少个数。第二问单独问，是因为分频系数和重装载值都有取值范围，凑出来的数必须落在硬件能表达的区间里。第三问要注意 WWDG 的计数器从 0x3F 递减，所以总周期是 64 个计数，而不是「减到 0 的次数」。

步骤：

1. 选预分频系数：IWDG 的预分频有 4、8、16、32、64、128、256 一类（即 $\div 4$ 到 $\div 256$ 的 2 的幂档），重装载是 12 位（0 ~ 4095）。先试 $\div 64$：计数频率 $= 40000 / 64 = 625\ \text{Hz}$，即每秒 625 个脉冲。
2. 求重装载值：4 秒需要 $4 \times 625 = 2500$ 个脉冲，而计数是从 0 数到重装载值共「重装载值 + 1」个，所以重装载 $= 2500 - 1 = 2499$。
3. 能力范围检查：$\div 64$ 下最长超时 $= (4095 + 1) \times 64 / 40000 = 6.5536$ s，4 s 放得下 ✓；$\div 256$ 下最长 $= (4095+1) \times 256 / 40000 = 26.2144$ s，这已经是 IWDG 的全局最长超时，再往上没有了。所以 4 秒这个目标，$\div 64$ / 2499 是可行的。
4. WWDG：计数频率 $f_{tick} = 36\times10^6 / 8 = 4.5\ \text{MHz}$，一个计数值对应 $t_{tick} = 1/4.5\ \text{MHz} = 222.22\ \text{ns}$。总超时 $= 64 \times t_{tick} = 14.22\ \mu s$。WWDG 的计数器从 0x3F 递减，若窗口阈值设为 0x3C，则窗口期 $= (0x3F - 0x3C) \times t_{tick} = 3 \times 222.22\ \text{ns} = 0.667\ \mu s$；若窗口阈值取 0x3F（刚启动就开窗），窗口期就是整个 14.22 µs。

$$T_{out} = \frac{(\text{重装载值} + 1) \times \text{预分频系数}}{f_{LSI}} = \frac{2500 \times 64}{40000} = 4.0\ \text{s}$$

$$\text{IWDG 最长超时} = \frac{(4095+1) \times 256}{40000} = 26.2144\ \text{s}$$

回代验算：把 $\div 64$ 代回公式，$2500 \times 64 = 160000$，$160000 / 40000 = 4.0$ s ✓。再从另一头验：计数频率 $625$ Hz，2500 个脉冲 $\Rightarrow 2500/625 = 4.0$ s ✓。WWDG 侧：$64 \times 8 / 36\times10^6 = 1.4222\times10^{-5}$ s = 14.22 µs ✓（$\mu$s 这个量级说明 WWDG 只能抓「毫秒级」的程序节奏问题，不可能当超时看门狗用）。

```c
hiwdg.Instance = IWDG;
hiwdg.Init.Prescaler = IWDG_PRESCALER_64;
hiwdg.Init.Reload = 2499;
HAL_IWDG_Init(&hiwdg);
// 主循环末尾
HAL_IWDG_Refresh(&hiwdg);
```

一条工程结论：IWDG 最长只能到 26.2 s，所以它适合做几秒到几十秒的兜底；更长的监控周期（比如 5 分钟）要用 RTC 的闹钟或另一个定时器中断来计数，而不是硬撑 IWDG。
:::

看门狗管的是程序死了。该管程序要能改了，而 Flash 有个硬脾气：不能像 RAM 那样就地改写。

「不能把 0 变回 1」为什么会是大事？因为它意味着你不能只改一个字节。想把第 7 个字节从 0x00 改成 0xFF，你必须擦掉它所在的整页（1024 字节），再把整页里另外 1023 个字节的内容重新写一遍。两条工程纪律就是从这儿来的。

1. 变化频繁的数据不要放 Flash。参数、计数器、日志请放 EEPROM（STM32F1 没有独立 EEPROM 时用 Flash 模拟，或者外挂一颗 EEPROM 芯片），或者放备份域 SRAM。
2. 代码和会变化的数据别挤在同一页。你的 App 代码最后半页后面要是紧跟着配置区，那「改一个配置」就会把半个 App 擦掉重写。

### 3.2 寿命：擦写次数是有限的

Flash 每个页的擦写次数（endurance）有限，典型值 1 万次，工程上按「至少 1 万次」保守设计。这个次数按页算：擦一次整页，整页的寿命减一。

算法简单，但常常被搞错。假设一页 1 KB，你每写一条记录占 16 字节，一页能装 64 条记录。要把这页写满 1 万次，一共能写 $64 \times 10000 = 640\,000$ 条记录。每 10 分钟一条的话，寿命是 $640\,000 \times 10$ 分钟 = 6 400 000 分钟 = 444 天，约 1.2 年。

1.2 年这个数字说明，如果你要的是「十年不掉数据」，就不能靠 Flash 裸存，得换策略：环形缓冲（写满一页就擦下一页，寿命按均匀擦除摊薄）、双页交替（ping-pong），或者外挂 FRAM/EEPROM。

::: tip 例 3 · 一页 Flash 能撑多久
**题目**：某记录仪每 10 分钟写一条 16 字节的记录，Flash 页大小 1 KB，擦写寿命 1 万次。问：这页能记录多少条数据？按这个速率能撑多久？

先猜一个量级：一条 16 字节、10 分钟一条，一页 1 KB 装 64 条，一天 144 条，怎么也得撑上一年半载。再动手算。顺序是先算「一页装几条」（除法，注意向下取整），再乘寿命次数。注意这是页的寿命，不是每字节的寿命，很多人误以为每写一条记录寿命减一，那就少算了几万倍。

步骤：

1. 一页装多少条：$1024 / 16 = 64$ 条 ✓。
2. 总共能写：$64 \times 10000 = 640\,000$ 条。
3. 换算成时间：$640\,000 \times 10$ 分钟 $= 6\,400\,000$ 分钟 $= 6\,400\,000 / 60 / 24 = 444.4$ 天，约 1.22 年。

回代验算：反向验算，444.4 天 $\times$ 每天 144 条（每 10 分钟一条，$24\times6 = 144$）$= 63\,994$ 条/天，$\times 444.4$ 天 ≈ 640 000 条 ✓。寿命本身再验一次：$64 \times 10000 = 640\,000$ ✓。
:::

### 3.3 IAP：Bootloader 与 App 分区

- Bootloader（引导程序）：复位后第一段执行的代码。它做三件事，检查是不是要升级、检查新固件是否完整、跳到该运行的 App；
- App（应用程序）：你写的业务代码。

一次完整的升级大致是这样走的。

1. 上位机把新固件通过串口/USB/网络传给设备，设备写进非当前的那个 App 分区（写之前先擦掉它）。
2. 写完之后做校验，最常用的是 CRC32：把整段固件按一个多项式算出一个 32 位校验码，接收端算一遍，对得上才算数。CRC 能查出传输过程中的位错误（bit error），但防不了恶意篡改，要防篡改得用数字签名。
3. 校验通过后更新一个标志位（放在数据区），告诉 Bootloader「下次启动去 B 区跑」。
4. 复位，Bootloader 读标志位、跳转到新 App；新 App 运行正常后再把标志位清掉。

Bootloader 自己也得被保护。它要能被下载器访问才能下载新固件，但不应该能被普通应用随便改写。常见做法是把升级入口做成一条特殊命令（比如一条特定的串口指令），而不是开放一个「写 Flash」的通用接口。

至于 Bootloader 区为什么通常只有十几 KB，因为它只做检查、擦写、校验、跳转这四件事，不含业务逻辑，所以能小就小，留给 App 的空间越大。

RDP（Read-Debug Protection，读保护）一句话能说完：它把芯片的调试口锁上，让普通办法读不出 Flash 里的内容，还能顺带关掉 SRAM 调试。ST 芯片还有第二级 RDP，可以整机锁死，只能靠擦除整个芯片来恢复，这是量产锁定的最后一层保险。

### 3.4 例题：设计一个升级方案

::: tip 例 4 · 给一块 128 KB Flash 的板子设计 IAP 布局
**题目**：某设备有 128 KB Flash，App 固件 48 KB，需要支持现场升级。另有 20 KB 配置文件与日志区。请设计分区并说明升级流程中 Flash 的操作顺序。

先猜一个坏方案：只留一个 App 区。这样升级时你得擦掉正在运行的代码，擦到一半断电，设备就变砖。想清这一点，分区方案基本就定了。

步骤：

1. 分区：Bootloader 16 KB + App A 48 KB + App B 48 KB + 数据区 16 KB = 128 KB，恰好用满 ✓。
2. 升级写 App B：当前跑的是 App A，写 B 不影响正在运行的代码。
3. 擦写顺序：先擦 App B 所在的 48 个 1 KB 页（48 页），再逐字写入新固件，最后写 CRC 与版本号。*（为什么先擦后写：Flash 不能把 0 变 1，没擦干净的新内容会和旧内容按位与，写出来是错的。）*
4. 校验：对 48 KB 固件算 CRC32，与上位机传来的值比较。
5. 切换：CRC 对得上就写升级标志位，然后复位；Bootloader 看到标志位就跳 B 区。
6. 回滚：新 App 起来后如果自检不通过（比如关键外设初始化失败），就把标志位指回 A 区再复位。

回代验算：

- 空间：$16 + 48 + 48 + 16 = 128$ KB ✓ 恰好用满；
- 擦除代价：48 页 × 约 40 ms ≈ 1.92 s 的擦除时间（擦除期间 CPU 通常只能等在 FLASH 状态寄存器上，不能取指，所以要放在 RAM 里执行，或者干脆让出 CPU）；
- CRC 耗时：48 KB × 8 bit/字节 = 393 216 bit，按 100 MHz 下每 bit 几个周期估，约 4 ms，远小于擦除时间；
- 寿命：App B 区每升级一次消耗一次该页的寿命（1 万次），即使每天升级一次也能用 27 年。

还有一条纪律：升级标志位所在的页也会被反复擦写，所以别把标志位和普通日志写在同一页，否则日志写一次就消耗一次寿命。
:::

## 四、三块东西怎么配合：系统可靠性

把它们按「设备出了什么问题」排一排，关系就出来了。

| 出了什么事 | 靠谁解决 | 机制 |
| --- | --- | --- |
| 断电之后不知道现在几点 | RTC | 电池维持备份域供电，计数器继续走 |
| 设备要睡觉，隔一段时间醒一次干活 | RTC | 闹钟/唤醒定时器产生唤醒中断 |
| 程序跑飞 / 卡死循环 | 看门狗 | 超时自动复位；若要细分原因，配合备份域 SRAM 存现场 |
| 程序没死，但节奏乱 | 窗口看门狗 | 过早或过晚喂狗都判错 |
| 现场要改固件 | Flash + IAP | Bootloader 接收、擦除、编程、校验、切换 |
| 不想让别人读走固件 | RDP | 锁调试口 |

一句话串起来：RTC 保证掉电后时间要准，看门狗保证跑飞了能复位，Flash 与 IAP 保证固件能升级。三块凑齐，设备才从「能跑」走到「能长期无人值守地跑」。

它们之间还会互相配合。举个具体的例子，一台每 10 分钟醒一次的数据记录仪：

- 醒来的时刻由 RTC 唤醒定时器决定（不是主循环轮询），这样芯片 99% 的时间在低功耗状态，只在醒来的几十毫秒里干活；
- 醒来后先喂狗（证明主循环正常），然后采集、写入 Flash 的一页；
- 写满一页就擦下一页，但擦除前必须先喂狗，因为擦除要等 40 ms，这期间 CPU 不能执行代码，别让它被误判为卡死；
- 写日志前读一次 RTC，把「时间戳 + 数据 + CRC」一起写进去；
- 如果某次写入过程中掉电，备份域里的一个「写入中」标志没被清掉，下次启动时启动代码会发现它，丢弃这半页数据。宁可少一条，也不能让 CRC 对不上的脏数据留在日志里。

真要做一台新设备，上手顺序基本是固定的：1. 先把 RTC 和纽扣电池装好，让时间基准立住；2. 定采样节拍，用唤醒定时器而不是主循环轮询；3. 划好分区，先把 Bootloader 跑通；4. 挂上 IWDG，喂狗放在主循环末尾；5. 最后才做升级通路与回滚。顺序颠倒的代价是：前面每一步都得回头重测。

下一个问题跟着就来了：设备要放在野外、靠太阳能电池供电，Flash 每天写一次、每写一次擦一页，寿命怎么办？答案还是环形缓冲，写满一页擦下一页，每一页被均匀擦到，写 1 万次才轮完一圈。

## 五、工程实例

### 5.1 实例 A：带时间戳的数据记录仪

设备画像：一台记录振动数据的便携式设备。要求每 10 分钟采一次数据、每次采 4 KB、存进 Flash、每条记录带时间戳、连续工作 2 年以上、掉电后时间不能乱。

设计要点：

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 时间基准 | RTC + 纽扣电池 | 主电掉电时靠 VBAT 继续走时 |
| 采样节拍 | RTC 唤醒定时器（600 s） | 比常驻定时器省电，且节拍与时间戳严格对应 |
| 记录格式 | 16 字节：时间戳 4 + 数据 4 + CRC 4 + 序号 4 | 固定长度才能一页装整数条，页对齐 |
| 存储寿命 | 每页 64 条，1 万次擦写 | 640 000 条 × 10 min ≈ 444 天，不够 2 年 |
| 寿命对策 | 环形缓冲：写满一页擦下一页 | 擦除均匀分布，每页都要写满 1 万次才轮完 |
| 可靠性 | IWDG 4 s 超时，主循环喂狗 | 采集卡死时自动重启 |

按这个速率，一天要写进去 144 条、每条 4 KB，一天接近 576 KB，一年下来 200 MB 上下，Flash 的容量很快就见底，寿命账更得算到底。裸写只能撑 444 天 < 730 天（2 年），所以必须用环形缓冲。换成环形缓冲后，128 KB 共 128 页，每页可擦 1 万次，总擦除预算 $= 128 \times 10000 = 1\,280\,000$ 页次；每页装 64 条记录，总记录量 $= 1\,280\,000 \times 64 = 81\,920\,000$ 条。按每天 144 条算，寿命 $= 81\,920\,000 / 144 = 568\,889$ 天，约 1500 年。同一块 Flash，同一种记录格式，只因为擦除是按页摊的，寿命差出三个数量级。

掉电保护也顺手做掉：每次写之前，把「下一条要写的页号 + 序号」写进备份域 SRAM（不需要擦 Flash，几微秒就写完），写完后再更新。这样掉电后启动代码知道该从哪继续、上一条是不是写了一半（序号对不上就丢弃）。

### 5.2 实例 B：能在现场升级固件的设备

设备画像：一套放在客户现场的电机控制器。售后不能每次都派人过去换板子。

1. 分区：Bootloader 16 KB + App A 48 KB + App B 48 KB + 数据区 16 KB（与例 4 相同）；
2. 升级入口：监听一条专用串口命令（或 HTTP 接口），进入升级模式后停止当前 App、跳到 Bootloader 的下载函数；不要在 App 里长期挂着一个「任意地址可写 Flash」的接口；
3. 传输：分块传输，每块带序号，Bootloader 逐块写入非当前分区，写满一页自动擦下一页；
4. 校验：整包 CRC32；
5. 切换与回滚：写标志位 → 复位 → 跑新 App → 新 App 自检（关键外设初始化、传感器读数合理性）通过才把标志位清掉，不通过就自动回滚到旧分区；
6. 兜底：IWDG 与 RTC 在 Bootloader 里也必须继续跑，否则升级写一半掉电，设备连回滚的机会都没有。

升级过程中最危险的三件事，以及各自的解法：擦除时断电，用双分区，擦的不是当前分区就没事；固件传了一半 CRC 不对，校验不通过就不切标志位，继续跑旧固件；切换之后新固件本身有 bug，靠自检加自动回滚。

读保护还有个边界。量产时打开 RDP，防止别人用下载器把固件读走，但 RDP 打开后调试器连不上，Bootloader 也就没法通过调试器下载固件了。所以升级必须走一条非调试口的通路（串口/USB/网络），这一条要在设计之初就想清楚。

## 六、易错清单与考点速记

### 易错清单（按踩坑频率排序）

| 错误做法 | 会得到什么 | 正确做法 |
| --- | --- | --- |
| 在定时器中断里喂狗 | 主循环死了照样被喂狗，看门狗永远不响 | 在主循环末尾或「各任务报到成功」的统一位置喂 |
| 忘了开 RTC 备份域访问 | 复位后时间回到 2020-01-01，反复设时间也留不住 | 设好时间后立刻打开备份域写访问（并意识到它会让调试器不能再擦 Flash） |
| RTC 分频因子凑成非整数 | 计时漂移，一天差几分钟甚至完全停走 | 分频结果必须整除 32768；用可配的 PRL 那一级去凑 |
| 唤醒定时器装载 600 | 周期变成 601 秒 | 向下计数时装「目标秒数 − 1」 |
| 用 4 年一闰的简化规则 | 2100 年之后日期全错一天 | 完整规则：能被 4 整除、不能被 100 整除、或能被 400 整除 |
| 每写一条记录就擦一页 | 寿命从 10 万条掉到 1 万条 | 一页装满再擦；用环形缓冲让擦除均匀 |
| 想只改 Flash 里一个字节 | 改不了：0 不能直接变 1 | 擦整页 + 重写整页；或者把变化数据放到 EEPROM/备份域 SRAM |
| 代码和会变化的配置挤在同一页 | 改一次配置就把半个 App 擦掉 | 分区隔离，配置单独放一页或外部 EEPROM |
| Bootloader 和 App 都放同一分区 | 升级时擦掉正在跑的代码，变砖 | Bootloader 单独分区，升级写另一个 App 分区 |
| 升级不校验就切换 | 传了一半也跳过去，设备变砖 | CRC32 校验通过才写标志位；新 App 自检失败自动回滚 |
| 量产忘了开 RDP，或开了 RDP 才发现没法升级 | 前者固件被读走，后者设备再也升不了级 | 先定好非调试口的升级通路，再决定读保护等级 |
| 调试时在断点处停住 | 看门狗溢出复位，误以为是程序 bug | 调试期冻结看门狗（`__HAL_DBGMCU_FREEZE_IWDG()`） |

### 考点速记

- RTC 分频：$32768 \div 128 \div 256 = 1$ Hz；闰年规则「四百年一闰」。
- 唤醒定时器：向下计数，装载值 = 目标秒数 − 1。
- 备份域：VBAT 供电，主电掉电也保留 RTC 与少量 SRAM。
- IWDG 超时：$T_{out} = (\text{重装载}+1) \times \text{预分频} / f_{LSI}$；LSI ≈ 40 kHz；最长约 26.2 s。
- WWDG 窗口：两条判据（超时 + 过早）；总周期 = 64 个计数值；窗口期 = 允许的计数值个数 × tick。
- 喂狗位置：主循环末尾，或多任务报到成功后；不在定时器中断里。
- Flash 三动作：擦除（按页，耗寿命，慢）→ 编程（按字，耗寿命）→ 读（免费，快）。
- Flash 寿命：1 万次擦写，按页算；一页 1 KB 装 64 条 16 字节记录 → 640 000 条。
- IAP 分区：Bootloader（16 KB）+ App A + App B + 数据区；升级写非当前区 → CRC 校验 → 写标志位 → 复位 → 自检 → 回滚。
- RDP：锁调试口，防读走固件；一旦打开，升级必须走串口/USB/网络。
