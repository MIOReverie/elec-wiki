# 14 · RTC、看门狗与 Flash 编程

<Meta time="45 min" level="了解" note="三件事共用一条主线：时间要准、跑飞要能复位、固件要能改" />

**这一页要解决什么**：你的设备现在有三块心病。**时间不准**——设备晚上断电，第二天早上记的时间全乱了；**跑飞救不回来**——程序一进入死循环就砖了，必须拆下来接下载器；**固件改不了**——想修一个 bug，得把设备寄回工厂。读完这一页你应该能：算出 RTC 的分频因子与唤醒周期、算出看门狗的超时时间与允许喂狗的窗口、说清 Flash 的一次擦写与一次编程各自消耗了什么寿命，并能在纸上画出 Bootloader 与 App 的分区布局。

::: tip 读这页之前
- **需要会**：时钟树与各时钟源（<Prereq id="clock-tree" />）、寄存器「就是有地址的内存」（<Prereq id="register-map" />）、中断与 NVIC（<Prereq id="nvic-priority" />）。
- **需要会**（可选）：低功耗模式与唤醒源（[12 · 低功耗与综合项目](./lowpower-project.md)）、看门狗在低功耗章里已经出现过一次（[12 · 低功耗](./lowpower-project.md)），本章会把它讲透。
- **这一页用到的符号**：$f_{osc}$（**晶振频率**，RTC 用 32768 Hz 外部晶振）、$N_{pre}$（**预分频系数**，prescaler，把高频时钟除小到目标频率的整数因子）、$f_{tick}$（**计数频率**，分频后送给计数器每秒的脉冲数）、$T_{out}$（**超时时间**，watchdog 溢出前允许的最长间隔）、$T_{win}$（**窗口期**，window，看门狗允许喂狗的时间窗口宽度）、$ARR$（自动重装载值）、$N_{erase}$（**擦写次数**，flash endurance，单位次）。
- **七个词先给一句话**（正文会展开）：
  - **VBAT**：芯片上一枚专门给 RTC 和备份域供电的电池引脚，接纽扣电池后主电断掉，RTC 继续走时。
  - **备份域**（backup domain）：由 VBAT 供电的一小块电路，装着 RTC 的计数器、闹钟和一小片 SRAM，与主电源无关。
  - **预分频**：把一个频率除以一个整数，让高频时钟变慢到目标频率。
  - **窗口期**：一个「允许操作的时刻范围」。WWDG 在这个范围之外喂狗也算错。
  - **页擦除**（page erase）：Flash 只能整页清零，不能单独改写页里的某几个字节。
  - **IAP**（In-Application Programming，**在应用编程**）：应用程序自己调用内部 Flash 的编程接口改写自己所在的 Flash；**Bootloader** 是复位后先跑的那段小程序，负责判断该跳到哪个 App。
  - **RDP**（Read-Debug Protection，**读保护**）：把芯片的调试口锁上，让普通办法读不出 Flash 里的内容。
  - **LSI**（Low-Speed Internal，内部低速时钟）：芯片内部自带的约 40 kHz 振荡器，不依赖外部晶振，主要喂独立看门狗。
- **本章不涉及的数学**：只有乘除与取整，没有复数、没有微积分。
:::

先说三件具体的、几乎每台设备都会遇到的事。

第一，你的**数据记录仪**每天记一条读数，晚上设备被断电（或者厂里拉闸），第二天早上你发现它记的时间全部回到了 2020 年 1 月 1 日——因为 MCU 一上电是从 0 开始的，而它没有电池记住「现在是几点」。

第二，你的**电机控制器**偶尔会莫名其妙死机，指示灯还亮着，说明程序卡在了一个死循环里；你想用调试器连上去看，但程序跑飞时往往已经把内存搅乱，连上去什么都看不到，只能靠外部工具强行复位。

第三，你想给已经装在客户现场的设备**修一个 bug**，但它只有一块焊死的 Flash，你没法插下载器。

这三件事的解法其实是同一类东西：**让芯片自己多长一点「器官」**——一个掉电也记得时间的器官（RTC）、一个发现程序死了就自己重启的器官（看门狗）、以及一个能容纳并改写自己代码的器官（片上 Flash）。

## 结论先行

1. **RTC 的本质是一个「每秒减 1 的计数器」**：32.768 kHz 晶振经 128、256 两级分频正好得到 1 Hz，计数器每秒减一，溢出时把秒加一、清零、判闰年；分频因子不是随便凑的，它必须整除 32768。
2. **备份域 + VBAT 是「掉电不走时」的全部秘密**：只要 RTC 和备份域 SRAM 的供电没断，计数器里的时间就在；掉电保存靠的是电池，不是靠软件。
3. **独立看门狗用 LSI 计时，因此「主时钟挂了它还在数」**，这是它能救回跑飞程序的前提；窗口看门狗除了超时，还多一条「喂太早也是错」，用来抓程序节奏乱掉的情况。
4. **喂狗必须由「证明主流程还活着」的那段代码来做**，写在定时器中断里等于没开看门狗——中断在主循环死掉时照样会触发。
5. **Flash 不是 RAM，不能就地改写**：擦除以页为单位、编程以字为单位，一次擦除的寿命是一次，频繁擦同一页会把它写坏；IAP 升级靠的是「Bootloader + 双 App 分区 + 校验」这套组合。

## 一、RTC：让掉电之后时间还是对的

这一节只回答一个问题：**一台没有电池的芯片，凭什么知道现在几点**。

### 1.1 一条分频链：32768 → 1 Hz

RTC（Real-Time Clock，实时时钟）是一个**只跟一个外部晶振绑死**的模块。它不挂在系统主时钟上，所以哪怕 CPU 时钟配置错了、主时钟停了，RTC 照样走。

**为什么是 32.768 kHz**，一句话：因为 $32768 = 2^{15}$，用两次「二分频」就能从它得到 1 Hz，而分频器做二分频是数字电路里最简单、最准的一件事；频率选成 2 的整数次幂之外的值，就得用麻烦得多的除法器。同时 32.768 kHz 落在人耳听觉下限之下（人耳约 20 Hz ~ 20 kHz），所以它安静、且对辐射与功耗都友好。

**「预分频」到底是什么**：它是计数器前面的一个「每 N 个脉冲才放行一个」的闸门。晶振每秒敲 32768 下，预分频 128 之后闸门只放行 256 下/秒，再经 256 分频，就只剩 1 下/秒。**分频系数越大，计时越慢、分辨率越低**——这是所有分频链的共同代价。

### 1.2 从秒到年月日：计数器怎么进位

拿到 1 Hz 之后，剩下的就是纯数字逻辑，跟你手算的电子表一样：

- **预分频计数器（PRL）**：接 1 Hz，每秒减 1，减到 0 溢出，产生一个「秒更新」事件；
- **秒/分/时计数器**：每收到一次秒更新就加一，秒从 59 变 60 就清零并给分钟进一；
- **日期计数器**：知道每个月的天数（28/29/30/31）和闰年规则（第 4 年一闰，百年号除 400 的才闰）。

**闰年规则**为什么要单独说：教科书里的「四年一闰」在 2100 年会错。公历的完整规则是：**能被 4 整除但不能被 100 整除的年要闰；能被 400 整除的年照闰**。1996 年闰、2000 年闰、1900 年不闰、2100 年不闰。写进代码时别偷懒。

### 1.3 闹钟、唤醒与备份域

RTC 除了「报时」，还有两个实用功能：

- **闹钟（alarm）**：到某个时刻产生一个中断。你可以用它在低功耗设备里定时唤醒 MCU——这比「一直开着定时器轮询」省电得多；
- **唤醒（wake-up timer）**：一个可编程的倒计时，到点产生一次唤醒事件。

**一条工程纪律**：把 RTC 的时间设对之后，**必须把「后备寄存器」打开**（STM32 上是 `RCC_BDCR` 里的备份域访问使能），否则每次复位后 RTC 会被重新初始化，时间又白设了。这个开关还有连带效应——**它被打开过之后，普通调试器就不能再改写 Flash 了**（因为调试口的擦除 Flash 会破坏备份域），所以要改程序得先把备份域写保护打开再复位。

**步骤**：

1. **分频因子**：$32768 / 128 = 256\ \text{Hz}$，再 $256 / 256 = 1\ \text{Hz}$ ✓。*（为什么先除 128：STM32F1 的 RTC 内部固定是「PRL 预分频（可配 20 位）+ 128 + 256」两级，128 和 256 是硬件焊死的，只有最前面那级 PRL 可配。所以「可配因子」必须让最终结果是 32768 的整数倍。）*
2. **唤醒周期**：10 分钟 = 600 秒。唤醒定时器直接数秒，所以计数器装载 **599**。*（为什么是 599 不是 600：定时器是「装载值 → 减到 0 触发」的向下计数，装 599 时它数 599、598 … 1、0，一共经过 600 个 1 Hz 脉冲间隔，也就是 600 秒整。如果装 600，就变成 601 秒。）*
3. **一年多少秒**：2024 年是闰年（能被 4 整除、不能被 100 整除、且 2024 ÷ 4 = 506 没有余数），全年 366 天。

$$366 \times 24 \times 3600 = 31\,622\,400\ \text{s}$$

**验算**：用 RTC 自己的算法反推——2024-01-01 到 2025-01-01，跨过的月份天数是 31 + 29（2 月，闰年）+ 31 + 30 + 31 + 30 + 31 + 31 + 30 + 31 + 30 + 31 = 366 天；再乘 86400 s/天得 31 622 400 ✓。另外用软件交叉验算：`366 * 24 * 3600 === 31622400` 为真 ✓。再算一遍分频：$128 \times 256 = 32768$，$32768 / 32768 = 1$ ✓。
:::

**这一节的三句话**：分频因子要整除 32768；唤醒定时器数的是秒、装载值要减一；闰年规则是「四百年一闰」。下一节看另一个器官：**程序死了，谁来发现**。

## 二、看门狗：跑飞了怎么自己回来

这一节只回答一个问题：**程序卡死时，谁能让芯片自己重启**。

答案是看门狗（watchdog）：一个**独立的定时器，不喂它就复位整个芯片**。

| 对比项 | IWDG（独立看门狗） | WWDG（窗口看门狗） |
| --- | --- | --- |

| 判据 | 只有「超时」 | 「超时」+「太早」 |

**为什么 IWDG 用 LSI 就等于「独立」**：LSI 是芯片内部自带的振荡器（**内部低速时钟**，Low-Speed Internal），完全不需要外部晶振，它的供电与时钟树、和 HSE/PLL 那条路没有任何关系。所以即使你把时钟树配错了、卡在启动阶段，IWDG 依然在正常计时并最终复位芯片——**这正是「独立」二字的全部含义**。WWDG 用 PCLK，主时钟一挂它跟着停，兜底能力就消失了。

**WWDG 的「窗口」是什么意思**：它把整个超时周期分成两段——**窗口期**（window，允许喂狗的那一小段时间）和「开口期」。WWDG 一启动，窗口是**关闭**的，你喂得太早会被判为错误；只有等到计数器减到某个阈值以下，窗口才打开，这时喂狗才算数。所以：

- 喂得**太早** → 复位（程序节奏不正常，循环跑得太快）；
- 喂得**太晚** → 复位（程序卡住了）。

这让 WWDG 能抓到 IWDG 抓不到的一类故障：**程序没死，但跑得不对**。

**喂狗必须放在「能证明主流程还活着」的位置**。这一条是看门狗使用里最容易搞错的地方：

- ✅ **主循环末尾喂狗**：主循环能转到这一行，说明整条流程还在正常流转；
- ❌ **在定时器中断里喂狗**：定时器中断是硬件机制，**主循环卡死时它照样按时触发**。这样「主循环已死」这个本该报警的故障会被中断喂狗掩盖掉，看门狗永远不会响——等于白开；
- ✅ **RTOS 里用事件组报到**：让每个关键任务各自「报到」，全部报到才由一个任务统一喂狗。这样任何一个任务单独卡死都能被检出。

::: warning 一个必然的副作用
看门狗复位会**丢掉复位原因以外的所有现场**。所以生产设备通常在喂狗前把关键状态写进备份域 SRAM 或 Flash，复位后由启动代码读出来上报（例如「上次是因为看门狗复位，任务 3 没报到」）。否则你只会看到一个永远重启、原因不明的设备。
:::

### 2.3 例题：算 IWDG 超时时间与 WWDG 窗口

::: tip 例 2 · 配一个 4 秒超时的 IWDG，并检查 WWDG 的喂狗窗口
**题目**：

1. LSI ≈ 40 kHz。要 IWDG 在 **4 秒**后复位，选预分频系数与重装载值各是多少？
2. 这个 4 秒超时是否落在 IWDG 的能力范围内？
3. 若 WWDG 的时钟是 PCLK = 36 MHz，预分频 8，请给出：一个计数值对应多少时间、总超时时间多长、窗口期多宽？

**先想什么**：先把「计数频率」和「计数个数」分开，不要直接套公式——分子是「数了多少个数」，分母是「每秒数多少个数」。第二问之所以要单独问，是因为**分频系数和重装载值都有取值范围**，凑出来的数必须落在硬件能表达的区间里。第三问要注意 WWDG 的计数器是**从 0x3F 递减**，所以总周期是 64 个计数而不是「减到 0 的次数」。

**步骤**：

1. **选预分频系数**：IWDG 的预分频有 4 档（4、8、16、32、64、128、256 一类，即 $\div 4$ 到 $\div 256$ 的 2 的幂档），重装载是 12 位（0 ~ 4095）。先试 $\div 64$：计数频率 $= 40000 / 64 = 625\ \text{Hz}$，即每秒 625 个脉冲。
2. **求重装载值**：4 秒需要 $4 \times 625 = 2500$ 个脉冲，而计数是从 0 数到重装载值共「重装载值 + 1」个，所以重装载 $= 2500 - 1 = 2499$。
3. **能力范围检查**：$\div 64$ 下最长超时 $= (4095 + 1) \times 64 / 40000 = 6.5536$ s，4 s 放得下 ✓；$\div 256$ 下最长 $= (4095+1) \times 256 / 40000 = 26.2144$ s，这已经是 **IWDG 的全局最长超时**，再往上没有了。所以 4 秒这个目标，$\div 64$ / 2499 是可行的。
4. **WWDG**：计数频率 $f_{tick} = 36\times10^6 / 8 = 4.5\ \text{MHz}$，一个计数值对应 $t_{tick} = 1/4.5\ \text{MHz} = 222.22\ \text{ns}$。总超时 $= 64 \times t_{tick} = 14.22\ \mu s$。WWDG 的计数器从 0x3F 递减，若窗口阈值设为 0x3C，则窗口期 $= (0x3F - 0x3C) \times t_{tick} = 3 \times 222.22\ \text{ns} = 0.667\ \mu s$；若窗口阈值取 0x3F（刚启动就开窗），窗口期就是整个 14.22 µs。

$$T_{out} = \frac{(\text{重装载值} + 1) \times \text{预分频系数}}{f_{LSI}} = \frac{2500 \times 64}{40000} = 4.0\ \text{s}$$

$$\text{IWDG 最长超时} = \frac{(4095+1) \times 256}{40000} = 26.2144\ \text{s}$$

**验算**：把 $\div 64$ 代入公式，$2500 \times 64 = 160000$，$160000 / 40000 = 4.0$ s ✓。再从另一头验：计数频率 $625$ Hz，2500 个脉冲 $\Rightarrow 2500/625 = 4.0$ s ✓。WWDG 侧：$64 \times 8 / 36\times10^6 = 1.4222\times10^{-5}$ s = 14.22 µs ✓（$\mu$s 这个量级说明 WWDG 只能抓「毫秒级」的程序节奏问题，不可能当超时看门狗用）。

```c
hiwdg.Instance = IWDG;
hiwdg.Init.Prescaler = IWDG_PRESCALER_64;
hiwdg.Init.Reload = 2499;
HAL_IWDG_Init(&hiwdg);
// 主循环末尾
HAL_IWDG_Refresh(&hiwdg);
```

**一条工程结论**：IWDG 最长只能到 26.2 s，所以它适合做「几秒到几十秒」的兜底；更长的监控周期（比如 5 分钟）要用 RTC 的闹钟或另一个定时器中断来计数，而不是硬撑 IWDG。
:::

看门狗解决的是「程序死了」。下一节解决「程序要能改」——但 Flash 有个硬脾气：**不能像 RAM 那样就地改写**。

## 三、Flash 编程：让固件可以被改写

### 3.1 Flash 的脾性：擦、编程、写保护

片上 Flash（片内存储器）是 **NOR 型**闪存，结构上决定了两条规矩：

| 操作 | 单位 | 作用 | 代价 |
| --- | --- | --- | --- |
| **擦除**（erase） | **页**（page） | 把整页恢复成全 1 | 慢（几十毫秒），**消耗一次寿命** |
| **编程**（program） | **字**（word，STM32 上 32 位） | 把字从 1 写成需要的值 | 中等速度，**也消耗寿命** |
| **读**（read） | 字 | 任意地址读 | 快，无消耗 |

**为什么「不能把 0 变回 1」是大事**：因为这意味着你**不能只改一个字节**。想把第 7 个字节从 0x00 改成 0xFF，你必须擦掉它所在的整页（1024 字节），然后把这一页里另外 1023 个字节的内容**重新写一遍**。这就引出两条工程纪律：

1. **不要把变化频繁的数据放在 Flash 里**。变化的参数、计数器、日志请放 **EEPROM**（STM32F1 没有独立 EEPROM 时用 Flash 模拟，或用外部 EEPROM 芯片），或者放备份域 SRAM（会掉电丢失的那部分）。
2. **别把代码和会变化的数据挤在同一页**。如果你的 App 代码最后半页后面紧接着是配置区，那么「改一个配置」就会把半个 App 擦掉重写。

### 3.2 寿命：擦写次数是有限的

Flash 每个页的**擦写次数**（endurance）是有限的，典型值 **1 万次**（工程上按「至少 1 万次」保守设计）。这个次数是**按页**算的：擦一次整页，整页的寿命减一。

**寿命的算法很简单，但常常被搞错**。假设一页 1 KB，你每写一条记录占 16 字节，一页能装 64 条记录。要把这一页写满 1 万次，一共能写 $64 \times 10000 = 640\,000$ 条记录。每 10 分钟一条的话，寿命是 $640\,000 \times 10$ 分钟 = 6 400 000 分钟 = 444 天，约 **1.2 年**。

**这个数字说明什么**：如果你要的是「十年不掉数据」，就不能靠 Flash 裸存，必须换策略——环形缓冲（写满一页就擦下一页，寿命按均匀擦除摊薄）、双页交替（ping-pong）、或者外挂 FRAM/EEPROM。

::: tip 例 3 · 一页 Flash 能撑多久
**题目**：某记录仪每 10 分钟写一条 16 字节的记录，Flash 页大小 1 KB，擦写寿命 1 万次。问：这一页能记录多少条数据？按这个速率能撑多久？

**先想什么**：先算「一页装几条」（除法，注意要向下取整），再乘寿命次数（这是**页**的寿命，不是每字节的寿命——很多人误以为每写一条记录寿命减一，那就少算了几万倍）。

**步骤**：

1. 一页装多少条：$1024 / 16 = 64$ 条 ✓。
2. 总共能写：$64 \times 10000 = 640\,000$ 条。
3. 换算成时间：$640\,000 \times 10$ 分钟 $= 6\,400\,000$ 分钟 $= 6\,400\,000 / 60 / 24 = 444.4$ 天，约 **1.22 年**。

**验算**：反向验算——444.4 天 $\times$ 每天 144 条（每 10 分钟一条，$24\times6 = 144$）$= 63\,994$ 条/天，$\times 444.4$ 天 ≈ 640 000 条 ✓。再验寿命本身：$64 \times 10000 = 640\,000$ ✓。
:::

### 3.3 IAP：Bootloader 与 App 分区

**IAP**（In-Application Programming，在应用编程）指的是**应用程序自己调用 Flash 编程接口来改写 Flash**。要支持 IAP，Flash 里必须同时住着两样东西：

- **Bootloader**（引导程序）：复位后**第一段**执行的代码。它做三件事：检查是不是要升级、检查新固件是否完整、跳到该运行的 App；
- **App**（应用程序）：你写的业务代码。

**一次完整的 IAP 升级流程**大致是这样：

1. **上位机把新固件通过串口/USB/网络传给设备**，设备写进**非当前**的那个 App 分区（写之前先擦掉它）；
2. **写完之后做校验**：最常用的是 **CRC32**——把整段固件按一个多项式算出一个 32 位校验码，接收端算一遍对得上才算数。CRC 能查出传输过程中的位错误（bit error），但**不能防恶意篡改**——要防篡改得用数字签名；
3. **校验通过后更新一个标志位**（放在数据区），告诉 Bootloader「下次启动去 B 区跑」；
4. **复位**，Bootloader 读标志位、跳转到新 App；新 App 运行正常后再把标志位清掉。

**Bootloader 必须自己也被保护**：它要能被下载器访问才能下载新固件，但**不应该能被普通应用随便改写**。常见的做法是把升级入口做成一条特殊命令（比如一条特定的串口指令），而不是开放一个「写 Flash」的通用接口。

**为什么 Bootloader 区通常很小（十几 KB）**：它只做「检查、擦写、校验、跳转」四件事，不含业务逻辑，所以越小越好——留给 App 的空间越大。

**RDP**（Read-Debug Protection，读保护）是一句话的事：它把芯片的调试口锁上，**让普通办法读不出 Flash 里的内容**（还能顺带关掉 SRAM 调试）。ST 芯片还有第二级 RDP，可以整机锁死、只能靠擦除整个芯片来恢复——这是「量产锁定」的最后一层保险。

### 3.4 例题：设计一个升级方案

::: tip 例 4 · 给一块 128 KB Flash 的板子设计 IAP 布局
**题目**：某设备有 128 KB Flash，App 固件 48 KB，需要支持现场升级。另有 20 KB 配置文件与日志区。请设计分区并说明升级流程中 Flash 的操作顺序。

**先想什么**：先把 **128 KB 分给谁** 算清楚，再决定「升级写哪块」。最容易犯的错是只留一个 App 区——那样升级时你得擦掉正在运行的代码，擦到一半断电，设备就变砖了。

**步骤**：

1. **分区**：Bootloader 16 KB + App A 48 KB + App B 48 KB + 数据区 16 KB = 128 KB，恰好用满 ✓。
2. **升级写 App B**：因为当前跑的是 App A，写 B 不影响正在运行的代码。
3. **擦写顺序**：先擦 App B 所在的 48 个 1 KB 页（48 页），再逐字写入新固件，最后写 CRC 与版本号。*（为什么先擦后写：Flash 不能把 0 变 1，不擦干净的新内容会和旧内容按位与，写出来是错的。）*
4. **校验**：对 48 KB 固件算 CRC32，与上位机传来的值比较。
5. **切换**：CRC 对得上就写升级标志位，然后复位；Bootloader 看到标志位就跳 B 区。
6. **回滚**：新 App 起来后如果自检不通过（比如关键外设初始化失败），就把标志位指回 A 区再复位。

**验算**：

- 空间：$16 + 48 + 48 + 16 = 128$ KB ✓ 恰好用满；
- 擦除代价：48 页 × 约 40 ms ≈ 1.92 s 的擦除时间（擦除期间 CPU 通常只能等在 FLASH 状态寄存器上，**不能取指**，所以要放在 RAM 里执行的函数或让出 CPU）；
- CRC 耗时：48 KB × 8 bit/字节 = 393 216 bit，按 100 MHz 下每 bit 几个周期估，约 **4 ms**，远小于擦除时间；
- 寿命：App B 区每升级一次消耗一次该页的寿命（1 万次），即使每天升级一次也能用 27 年。

**一条纪律**：升级标志位所在的页也会被反复擦写，所以**不要把标志位和普通日志写在同一页**，否则日志写一次就消耗一次寿命。
:::

Flash 的事讲完了。现在把三块拼起来——它们其实在解决同一个问题的三个侧面。

## 四、一条主线：系统可靠性

这一节只回答一个问题：**RTC、看门狗、Flash 放在一起看，是什么关系**。

把它们按「设备出了什么问题」来排，就一目了然：

| 出了什么事 | 靠谁解决 | 机制 |
| --- | --- | --- |
| 断电之后不知道现在几点 | **RTC** | 电池维持备份域供电，计数器继续走 |
| 设备要睡觉，隔一段时间醒一次干活 | **RTC** | 闹钟/唤醒定时器产生唤醒中断 |
| 程序跑飞 / 卡死循环 | **看门狗** | 超时自动复位；若要细分原因，配合备份域 SRAM 存现场 |
| 程序没死，但节奏乱 | **窗口看门狗** | 过早或过晚喂狗都判错 |
| 现场要改固件 | **Flash + IAP** | Bootloader 接收、擦除、编程、校验、切换 |
| 不想让别人读走固件 | **RDP** | 锁调试口 |

**一句话串起来**：**RTC 保证「掉电后时间要准」，看门狗保证「跑飞了能复位」，Flash 与 IAP 保证「固件能升级」**。三者合起来是一个设备从「能跑」到「能长期无人值守地跑」的三块地基。

**它们互相之间也有配合**。举一个具体的例子：一个每 10 分钟醒一次的数据记录仪。

- 醒来的时刻由 **RTC 唤醒定时器**决定（不是主循环轮询），这样芯片 99% 的时间在低功耗状态，只在醒来的几十毫秒里干活；
- 醒来后先**喂狗**（证明主循环正常），然后采集、写入 Flash 的一页；
- 写满一页就擦下一页——但**擦除前必须先喂狗**，因为擦除要等 40 ms，这期间 CPU 不能执行代码，别让它被误判为卡死；
- 写日志前读一次 RTC，把「时间戳 + 数据 + CRC」一起写进去；
- 如果某次写入过程中掉电，备份域里的一个「写入中」标志没被清掉，下次启动时启动代码会发现它，丢弃这半页数据（宁可少一条，也不能让 CRC 对不上的脏数据留在日志里）。

**下一个问题就来了**：如果设备要放在野外、靠太阳能电池供电，Flash 每天写一次、每写一次擦一页，寿命怎么办？答案就是前面提到的**环形缓冲**：写满一页擦下一页，每一页被均匀擦到，写 1 万次才轮完一圈。

## 五、工程实例

这一节只回答一个问题：**把上面三块东西装到具体设备上，会遇到什么取舍**。

### 5.1 实例 A：带时间戳的数据记录仪

**设备画像**：一台记录振动数据的便携式设备。要求每 10 分钟采一次数据、每次采 4 KB、存进 Flash、每条记录带时间戳、连续工作 2 年以上、掉电后时间不能乱。

**设计要点**：

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 时间基准 | RTC + 纽扣电池 | 主电掉电时靠 VBAT 继续走时 |
| 采样节拍 | RTC 唤醒定时器（600 s） | 比常驻定时器省电，且节拍与时间戳严格对应 |
| 记录格式 | 16 字节：时间戳 4 + 数据 4 + CRC 4 + 序号 4 | 固定长度才能一页装整数条，页对齐 |
| 存储寿命 | 每页 64 条，1 万次擦写 | 640 000 条 × 10 min ≈ 444 天，不够 2 年 → 见下 |
| 寿命对策 | **环形缓冲**：写满一页擦下一页 | 擦除均匀分布，每页都要写满 1 万次才轮完 |
| 可靠性 | IWDG 4 s 超时，主循环喂狗 | 采集卡死时自动重启 |

**寿命账要算到底**：裸写只能撑 444 天 < 730 天（2 年），所以**必须用环形缓冲**。用环形缓冲后，128 KB 共 128 页，每页可擦 1 万次，总擦除预算 $= 128 \times 10000 = 1\,280\,000$ 页次；每页装 64 条记录，总记录量 $= 1\,280\,000 \times 64 = 81\,920\,000$ 条。按每天 144 条算，寿命 $= 81\,920\,000 / 144 = 568\,889$ 天，约 **1500 年**。**同一块 Flash，同一种记录格式，只因为「擦除是按页摊的」，寿命差出三个数量级。**

**掉电保护**：每次写之前，把「下一条要写的页号 + 序号」写进备份域 SRAM（不需要擦 Flash，几微秒就写完），写完后再更新。这样掉电后启动代码知道该从哪继续、上一条是不是写了一半（序号对不上就丢弃）。

### 5.2 实例 B：能在现场升级固件的设备

**设备画像**：一套放在客户现场的电机控制器。售后不能每次都派人过去换板子。

**设计要点**：

1. **分区**：Bootloader 16 KB + App A 48 KB + App B 48 KB + 数据区 16 KB（与例 4 相同）；
2. **升级入口**：监听一条专用串口命令（或 HTTP 接口），进入升级模式后**停止当前 App、跳到 Bootloader 的下载函数**；不要在 App 里长期挂着一个「任意地址可写 Flash」的接口；
3. **传输**：分块传输，每块带序号，Bootloader 逐块写入非当前分区；写满一页自动擦下一页；
4. **校验**：整包 CRC32；
5. **切换与回滚**：写标志位 → 复位 → 跑新 App → 新 App 自检（关键外设初始化、传感器读数合理性）通过才把标志位清掉，不通过就自动回滚到旧分区；
6. **兜底**：IWDG 与 RTC 在 Bootloader 里也必须继续跑，否则升级写一半掉电，设备连回滚的机会都没有。

**升级过程中最危险的三件事**：

- 擦除时断电（→ 用双分区，擦的不是当前分区就没事）；
- 固件传了一半 CRC 不对（→ 校验不通过就不切标志位，继续跑旧固件）；
- 切换之后新固件本身有 bug（→ 自检 + 自动回滚）。

**读保护的边界**：量产时打开 RDP，防止别人用下载器把固件读走。但要注意——**RDP 打开后调试器连不上，Bootloader 也就没法通过调试器下载固件了**。所以升级必须走一条非调试口的通路（串口/USB/网络），这一条要在设计之初就想清楚。

## 六、易错清单 + 考点速记

### 易错清单（按踩坑频率排序）

| 错误做法 | 会得到什么 | 正确做法 |
| --- | --- | --- |
| 在定时器中断里喂狗 | 主循环死了照样被喂狗，看门狗永远不响 | 在主循环末尾或「各任务报到成功」的统一位置喂 |
| 忘了开 RTC 备份域访问 | 复位后时间回到 2020-01-01，反复设时间也留不住 | 设好时间后立刻打开备份域写访问（并意识到它会让调试器不能再擦 Flash） |
| RTC 分频因子凑成非整数 | 计时漂移，一天差几分钟甚至完全停走 | 分频结果必须整除 32768；用可配的 PRL 那一级去凑 |
| 唤醒定时器装载 600 | 周期变成 601 秒 | 向下计数时装「目标秒数 − 1」 |
| 用 4 年一闰的简化规则 | 2100 年之后日期全错一天 | 完整规则：能被 4 整除、不能被 100 整除、或能被 400 整除 |
| 每写一条记录就擦一页 | 寿命从 10 万条掉到 1 万条 | 一页装满再擦；用环形缓冲让擦除均匀 |
| 想只改 Flash 里一个字节 | 改不了：0 不能直接变 1 | 擦整页 + 重写整页；或者把变化数据放到 EEPROM/备份域 SRAM |
| 代码和会变化的配置挤在同一页 | 改一次配置就把半个 App 擦掉 | 分区隔离，配置单独放一页或外部 EEPROM |
| Bootloader 和 App 都放同一分区 | 升级时擦掉正在跑的代码，变砖 | Bootloader 单独分区，升级写另一个 App 分区 |
| 升级不校验就切换 | 传了一半也跳过去，设备变砖 | CRC32 校验通过才写标志位；新 App 自检失败自动回滚 |
| 量产忘了开 RDP，或开了 RDP 才发现没法升级 | 前者固件被读走，后者设备再也升不了级 | 先定好非调试口的升级通路，再决定读保护等级 |
| 调试时在断点处停住 | 看门狗溢出复位，误以为是程序 bug | 调试期冻结看门狗（`__HAL_DBGMCU_FREEZE_IWDG()`） |

### 考点速记

- **RTC 分频**：$32768 \div 128 \div 256 = 1$ Hz；闰年规则「四百年一闰」。
- **唤醒定时器**：向下计数，装载值 = 目标秒数 − 1。
- **备份域**：VBAT 供电，主电掉电也保留 RTC 与少量 SRAM。
- **IWDG 超时**：$T_{out} = (\text{重装载}+1) \times \text{预分频} / f_{LSI}$；LSI ≈ 40 kHz；最长约 26.2 s。
- **WWDG 窗口**：两条判据（超时 + 过早）；总周期 = 64 个计数值；窗口期 = 允许的计数值个数 × tick。
- **喂狗位置**：主循环末尾，或多任务报到成功后；**不在定时器中断里**。
- **Flash 三动作**：擦除（按页，耗寿命，慢）→ 编程（按字，耗寿命）→ 读（免费，快）。
- **Flash 寿命**：1 万次擦写，按页算；一页 1 KB 装 64 条 16 字节记录 → 640 000 条。
- **IAP 分区**：Bootloader（16 KB）+ App A + App B + 数据区；升级写非当前区 → CRC 校验 → 写标志位 → 复位 → 自检 → 回滚。
- **RDP**：锁调试口，防读走固件；一旦打开，升级必须走串口/USB/网络。
